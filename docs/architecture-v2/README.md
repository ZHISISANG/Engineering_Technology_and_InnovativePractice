# 报销助手智能体系统 · 技术架构选型

面向"报销助手智能体"的一套可评审架构方案：**FastAPI 异步后端、LLM 经 API 接入且可替换、制度文档向量化检索、员工 / 管理员两角色**。方案只给结构与取舍，不含实现代码。

## 二、四个关键判断

1. **判定与生成分离**：版本是否生效、条款是否适用，用 SQL 与规则判定；模型只负责理解问题与组织表达。
2. **先过滤再相似**：按 `status=active`、生效区间、制度类别过滤后再做向量召回，避免"相似但已废止"的条款进入上下文。
3. **工具即权限边界**：注册表里没有 `submit_expense`，模型就不可能提交报销单；提交只能由人从前端触发。
4. **回答可回放**：消息落库时同时保存引用、提示词版本、模型与 token 用量，事后能解释"当时为什么这么答"。

## 三、第一周验收（摘要）

> 员工问"出差住宿标准是多少"，系统给出带条款引用的回答；问到制度里没有的内容时，明确回答"没有找到依据"，而不是编一个数字。

- 10 条问题：8 条可答且引用正确，2 条不可答必须拒答；
- 首字 ≤ 2.5s，整轮 p95 ≤ 10s；
- 员工调用管理员接口 100% 返回 403 并留审计；
- 每条回答都能在 `messages.citations` 找到来源。

## 四、边界

- 本期不做报销单提交与审批流、发票 OCR、多租户与细粒度权限；这些都在文档里写明原因。
- 数据量按千级片段设计；百万级以上向量需要重新评估存储选型。
- 成本数字均为量级估算，需以供应商账单与真实压测替换。
