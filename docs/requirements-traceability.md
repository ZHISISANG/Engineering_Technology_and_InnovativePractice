# 需求追溯矩阵

把 `discovery-requirements.csv` 的 6 条需求，逐条落到代码、测试、工具侧证据与业务侧待办。

> **读法**：`工具侧` 一栏是代码与演示数据能证明的部分；`业务侧` 一栏是仍需真人在真实试点里完成的部分。
> 两者不能互相替代。访谈覆盖率 36/36 也不等于验收通过。

## REQ-1 · 以版本有效期与确认状态替代文件名判断

| 项 | 内容 |
| --- | --- |
| 优先级 / 负责人 | P0 / 唐映秋（项目流程协调员） |
| 需求原文 | 以版本有效期+确认状态替代文件名判断，可减少旧通知引用导致的重复核对 |
| 证据 | f24（版本有效期）、f10（旧通知导致时间/费用口径不一致）、f11（展位调整后旧说明仍指原区域）、f12（虚构样本：900 次咨询、55% 重复——**不得当基线**） |
| 工具实现 | `core/versioning.py`：判定时点取业务发生时间；排序键 `(confirmed, not void, effective_from, confirmed_at, received_at, version_id)`，**不含文件名与 mtime**；作废记录保留 `void_reason`；草稿列出“已排除的版本”及理由 |
| 测试 | `tests/test_versioning.py` 11 项：`最新版_展位说明_最终版.pdf` 不参与判定；后到未确认不能覆盖已确认；过期→`NO_CURRENT_VERSION`；作废原因保留；双确认冲突；替代链；链断 |
| 工具侧证据 | 演示数据 16 单中 11 单可定位当前版本；5 单版本不可判定但全部进队列；T-1011 的“最新版”文件被明确列为“不参与判定” |
| 业务验收 | **未执行**。需按验收原文：单批次抽取含时间/费用说法的问答，标注“当前/过期/未确认”，流程协调员与审核方各复核一轮，以“能否定位当前版本”为通过条件；**不预设效率提升** |
| 残余风险 | 旧版本实际占比未知；“重复核对”是否真的减少无法由本工具证明；f12 为虚构样本，不能作为效果基线 |

| 业务验收 | **未执行**。需标注两类时间的比对差异，并模拟读取失败验证“快照 + 时间戳 + 人工核查提示”被业务方接受 |
| 残余风险 | 快照保留期限未定；“回填超过多久算异常”的 8 小时是默认值，需业务确认；历史回填数据无法还原真实发生时间 |

| 工具实现 | `core/metrics.py` 三项同时计算并输出公式；回填样本单列；返工=退回+重复确认；完整率=已确认项÷（工单×四项）；`core/feedback.py` + `expo-trace feedback` 登记误报/漏报/未确认并进入周报 |
| 测试 | `test_metrics.py`（452 分钟、返工 0、完整率 0/64、抽样确定性）、`test_feedback.py`（登记、校验、周报汇总） |
| 工具侧证据 | 报告并列 452 分钟 / 0 次 / 0.0%，且写明“只用工时判断效果会掩盖返工与确认不完整”；误报登记入口可用 |
| 业务验收 | **未执行**。需两个团队用同一周三项指标对账，并逐条复盘误报/漏报/未确认；确认“完成”定义是否被双方接受 |
| 残余风险 | 工时来自台账，台账本身可能不准；返工只统计工具内退回，线下返工看不到；完整率依赖人工如实提交 |

## 尚未核实的证据缺口

以下问题在材料中明确列为“未核实”，工具不能代替确认：

1. 旧版本在实际问答中的占比；
2. 统一关联编号由哪套系统生成、谁维护；
3. 快照保留期限与审计凭证保存期；
4. 例外认定权（谁有权认定“来源不完整/授权不清”可以放行）；
5. 两个团队共同接受的“完成”定义；
6. 草稿被误用后的恢复流程；
7. 正式抽查是否沿用 80 条；
8. 审计凭证的导出格式与保存地点。

在这些问题确认前，`acceptance.json` 的“业务验收”一行会一直是 `NOT_RUN`——这是设计，不是遗漏。
